# "Latest industry practice," made concrete

Each of these was a deliberate choice, not boilerplate — the reasoning is
what matters, not the checkbox.

## API versioning

`/api/v1` and `/admin/api/v1` now; a breaking v2 would mount alongside v1
(`app.include_router(v2_router, prefix="/api/v2")`), never an in-place
mutation of v1's contract. No v2 exists yet — this is a stated intent, not
built infrastructure.

## Hashed, not encrypted, API keys

`sha256`, never reversible. See
[07-auth-and-api-keys.md](./07-auth-and-api-keys.md) for the full
hash-vs-encrypt reasoning — this is the single most transferable security
concept in this whole codebase.

## Encrypted-at-rest provider/backend secrets, with fail-fast

`Fernet`, this service's own `ENCRYPTION_KEY`. Unlike a documented failure
mode in a sibling system this design was informed by (a service that
silently falls back to a throwaway, process-lifetime encryption key when
none is configured — meaning encrypted data becomes permanently
unreadable after every restart, with no error until someone notices),
`Settings.require_production_secrets()` is designed to fail fast at
startup in any non-development environment if `ENCRYPTION_KEY` or
`JWT_SECRET_KEY` is unset, rather than starting up "successfully" into a
state that will corrupt secrets on the next restart.

## Per-application rate limiting

In-memory sliding window (`app/core/rate_limit.py`), keyed by
`application_id`, with a per-application override falling back to a global
default. No Redis needed for a single-process deployment — the concrete
signal to revisit this: running this service with more than one uvicorn
worker, at which point an in-memory window no longer sees all requests.

## Idempotency

`Idempotency-Key` header on the three write endpoints
(`POST /memories`, `/batch`, `/{id}/supersede`) — a short-TTL
`idempotency_keys` table caches the exact prior response and replays it
verbatim on a repeated key, regardless of what the retried request body
says. Verified directly: sending the same `Idempotency-Key` twice with
*different* request bodies returned the identical first response both
times, and only one row was ever created. `search`/`delete` don't need
this — search has no side effect, delete is naturally idempotent.

## Health vs. readiness

See [09-observability-and-troubleshooting.md](./09-observability-and-troubleshooting.md).
A distinction worth having once other systems' orchestration depends on
this service being up — `/health` alone can't tell "process is running"
from "process can serve."

## Structured, durable request logging

See [09](./09-observability-and-troubleshooting.md). A SQL table, not an
in-memory trace — the whole point of building this as shared
infrastructure is that the people debugging a failure aren't the people
who can see this process's memory.

## Migration discipline, with one named exception

Alembic for every structural change to the control-plane schema — except
the per-application vector tables/files that `PgvectorAdapter`/
`SqliteVecAdapter` create dynamically at runtime, which are data-driven
(one per application, on demand) rather than fixed schema. This exception
is dangerous if forgotten: `alembic revision --autogenerate` will try to
`DROP TABLE` a dynamically-created `memory_vectors_*` table the first time
it runs after one exists, since it isn't part of the declared SQLAlchemy
models. This happened during development and was caught by reviewing the
generated migration before applying it — always review autogenerated
migrations in this codebase for exactly this pattern.

## Input validation at every boundary

Pydantic schemas on every request/response. `namespace`/`subject_id`/
`slug` have charset constraints beyond "any string" specifically because
they get interpolated into generated file/table/collection names
(`{slug}_g{generation}.db`, `memory_vectors_{slug}_g{n}`,
`app_{slug}_g{n}`) — `ApplicationCreate.SLUG_PATTERN` and
`MemoryCreate`'s namespace validator exist to make that interpolation safe
by construction, not by hoping every caller behaves.

## What was deliberately not added

No message queue, no Kubernetes, no service mesh — none justified by the
actual scale this service is designed for. Considered and rejected, not
overlooked; see the original design plan's non-goals table for the
concrete signal that would justify revisiting each.
